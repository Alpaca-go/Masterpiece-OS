# 气质框架（Style Framework）

状态：**两张草案 + 只读预检。** 不是规则库，也不是标杆检索；是"这一型应该长什么样、偏到哪里算跑偏"的坐标。

## 它解决什么问题

生图最容易出的错不是画得差，而是**漂到另一个业态**。真实例子：冯烫烫第一版是模型的默认提案——「浅色木 + 黑色不锈钢 + 3500K 明亮」，出来的就是商场效率快餐；但这个项目是社区底商，要的是暖黄偏暗、红砖旧木、有人有锅气的烟火感。

所以这一层不是"多写几句好话"，而是三件事：

1. **气质定义**：这一型是什么气质（用日常语言）；
2. **杠杆取值**：光/密度/材料/色面积/传统度/道具/文字/价格，落到机器可读的 8 个轴；
3. **反漂移信号**：哪些具体特征一出现，就说明被默认先验拉走了。

## 为什么放在"分析之后、编译之前"

- **分析之前**只能放项目事实与约束（面积、层高、街面/商场、堂食外带、时段、排烟）。这些不是气质，是条件。
- 先定气质再分析，会让分析按你的期望写 packet，"模型默认会漂到哪"这件最有价值的信息就消失了（冯烫烫那张卡正是记下了默认提案）。
- 编码层面，用户 tag > 分析提案；气质的落点就是 `styleControls`，编译前才有意义。

时序：

```
导入素材 → [事实与约束] → 分析（保持干净） → [选气质 + 预检] → 编译 → 生图 → 人工验收 → 回填 delta
```

## 和另外两层的关系

| | 案例卡 | 参考图集 | **气质卡（本层）** |
|---|---|---|---|
| 回答 | 为什么这样做、边界在哪 | 长什么样 | **这一型是什么气质、偏到哪算跑偏** |
| 产出 | 证据与先例 | 风格词汇 | 轴取值 + 反漂移清单 |
| 能升级为规则吗 | 可以（需多项目验证） | 不能 | 不能（它是坐标，不是结论） |

## 机器可读版本与同步规则

机器可读副本：`packages/visual-workflow/src/knowledge/style-presets.js`。

- UI 里"气质预设（草案）"下拉读的就是它；选中后**只填 8 个轴**，任何轴都可以再手改。
- 它**不会**自动把文字注入 Prompt；中文经验文本只用于展示与人工引用，避免绕过"显式传参"的基线。
- 改气质卡时两处一起改：`docs/knowledge/style-framework/<slug>.md` 与 `style-presets.js`；改完跑
  `npx tsx --test "packages/visual-workflow/tests/**/*.test.ts"`。

## 预检的口径（重要）

"按气质预检"是**只读提示**，不阻断生成：

- 它扫描的是编译后的 Prompt，而 Prompt 正文是英文，所以信号词也写成英文；
- 命中否定句（`no` / `avoid` / `not`）的行**不计**为跑偏——"不要白墙"正是我们要的约束；
- 会漏检（同义改写、隐含描述），所以只是提示，不是验收；
- 校验器 `passed` 也不等于验收；验收仍然只有人能签。

## 记录与回填（已实现）

选中气质后，任务契约里会多一个 `stylePreset` 字段：

```json
"stylePreset": { "id": "community-street-smoke", "label": "社区底商 · 烟火气", "axes": { "lighting": "warm_dim", "...": "..." } }
```

- `axes` 是**套用那一刻**的锚点取值，`styleControls` 是你最后决定的值；两者一减就是 delta（改过哪几个轴）。
- 这个字段**不进 Prompt**：编译器不读它，所以加不加预设、Prompt 都逐字节一致（2026-10-29 实测：同一任务两种请求 `finalPrompt` 完全相同，7697 字符）。
- 目前只做记录，还没有统计页面；下一步可以按 `stylePreset.id` 聚合「选了什么 / 改了什么 / 是否验收」。
