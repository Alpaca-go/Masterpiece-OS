# Short-Chain 功能精简方案

> **原则**：一个新用户打开产品，3 分钟内搞不懂怎么用，不是用户的问题——是产品的问题。
> 我们的目标是把"专家工具箱"变成"傻瓜相机"：默认简单，高级功能藏起来，需要时才出现。

## 2. 精简方案：做什么 / 不做什么

### 🔴 P0：必须做的（影响 80% 的新用户体验）

#### 2.1 合并"编译"和"生成"为一步

**现状**：用户需要先点"编译并生成"→ 右侧出现编译结果 → 再点"生成正式成果"。
两步操作，新用户搞不清"编译"是什么意思。

**精简方案**：
- 去掉"仅查看最终 Prompt"按钮
- "编译并生成"改成直接生成的按钮（叫"智能生成"）
- 编译过程在后台静默完成，用户不需要知道"编译"这个概念
- 编译失败时再显示错误（就像生成失败一样）

**理由**：
- 90% 的用户不会去手动编辑 Prompt
- "编译"是内部概念，用户只关心"点了之后能不能出图"
- 减少一次点击 = 减少一个流失节点
- Prompt 编辑功能保留，但移到生成后的详情面板里（"编辑 Prompt 重做"）

**工作量估计**：S — 主要是状态机调整，后端完全不动

---

#### 2.2 把"参考优先"从模式切换改成"上传了参考图就是参考优先"

**现状**：有一个"标准生成 / 参考优先"的模式切换。用户需要先切换模式，
再上传参考图。多一步决策，多一份困惑。

**精简方案**：
- 去掉模式切换按钮
- 默认就是"标准生成"
- 用户上传参考图后，自动进入"参考优先"模式（用一个徽章或小字提示）
- 移除所有参考图时，自动退回标准模式
- 高级设置里保留一个"关闭参考优先"的开关（给想只用参考图做素材、不强制风格的用户）

**理由**：
- 用户的心智模型是"我加了参考图，AI 当然会参考"，不需要显式切换模式
- Midjourney、Stable Diffusion 都是这样做的——加图就是图生图
- 减少一个主要决策点，降低认知负荷

**工作量估计**：S — 前端状态机调整，后端协议不变

---

#### 2.3 "成果物类型" + "子类型" + "镜头" 合并成一个"选模板"的流程

**现状**：先选 4 种大类（空间/包装/VI/海报），再在下拉里选子类型，
高级设置里再选镜头/构图。三步操作，层层嵌套。

**精简方案**：
- 改成一个"选择模板"的网格视图
- 每个模板卡片有：名称 + 缩略图占位 + 简短描述
- 点击模板自动设置好 family + subtype + shot + ratio
- "子类型"和"镜头/构图"下拉从主界面移除
- 想微调的用户可以去高级设置里改

**理由**：
- 新用户不知道"子类型"和"镜头"是什么意思
- 可视化的模板选择比两个下拉菜单直观 10 倍
- 减少决策次数：从 3 次选择（类别 + 子类型 + 镜头）变成 1 次

**工作量估计**：M — 需要设计模板卡片，但后端完全不动

---

#### 2.4 Logo 处理方式自动判断，不让用户选

**现状**：高级设置里有一个"Logo 处理方式"下拉，有 3 个选项，
其中一个还 disabled 了。新用户根本不知道该选哪个。

**精简方案**：
- 从 UI 中完全移除 Logo 处理方式的选择
- 自动判断规则（后端已经有了）：
  - 项目有确认的 Logo → 自动用 `post_composite`
  - 没有 Logo → 自动用 `blank_area`
- 高级用户可以在 Settings 里改默认行为（不是每个项目都改）

**理由**：
- 代码里已经有 30 多行的逻辑在处理"Logo 锁定时不能用 reference 模式"等边界情况
- 说明这个选择对用户太复杂，容易出错
- 正确的策略应该是产品帮用户选，而不是让用户猜

**工作量估计**：XS — 前端移除 UI，后端逻辑已经有了

---

### 🟡 P1：应该做的（中度影响，但很值得）

#### 2.5 "必须包含" / "必须避免" 合并进"本轮要求"

**现状**：三个 textarea：本轮要求、必须包含、必须避免。
用户不知道三者的区别和优先级。

**精简方案**：
- 只保留一个"创意要求"textarea（就是现在的"本轮要求"）
- "必须包含"和"必须避免"从主界面移除
- 在 textarea 下面放一行提示："可以写'必须包含 xxx'、'不要 xxx'等要求"
- 后端解析时自动识别 must_include / must_avoid 关键词（或者就全塞进 instruction 里）

**理由**：
- 普通人写 Prompt 不分这么细
- 三个输入框 = 三倍认知负担
- 自然语言比结构化输入对用户更友好
- 后端的 Prompt 编译器已经足够强大，可以从自然语言里提取约束

**工作量估计**：S — 前端改 UI，后端可能需要微调解析逻辑

---

#### 2.6 快捷反馈按钮（成果物不对/气质不对/Logo不对）改成一个"不满意"入口

**现状**：生成结果下面有三个按钮，直接往 instruction 里追加固定的纠偏文案。
功能很工程师思维，用户不一定理解点了会发生什么。

**精简方案**：
- 三个按钮合并成一个"对结果不满意？"文字链接
- 点击后展开 3 个选项（或者一个简单的文本框让用户说哪里不对）
- 保持现有的纠偏逻辑，但降低视觉权重

**理由**：
- 三个按钮摆在主操作区，抢了"沿用此方向"和"调整后重做"的风头
- 新用户第一眼看到"不对/不对/不对"会觉得"这个工具经常出错吗？"
- 这是进阶功能，不应该占据主视觉位置

**工作量估计**：XS

---

#### 2.7 "保存为项目级 Prompt 资产" 移到设置或隐藏

**现状**：这个功能我在代码里看到了 (`savePromptAsset`)，
但不确定在不在 UI 上。无论在不在，它都不应该在主工作流里。

**精简方案**：
- 如果在主界面上：移到 Prompt 编辑下拉菜单里
- 如果不在：保持现状

**理由**：
- 这是重度用户的高级功能，95% 的用户不会用
- 放在主界面上只会增加混乱

**工作量估计**：XS

---

### 🟢 P2：可以考虑的（锦上添花，不急）

#### 2.8 隐式参考系统的 UI 表达简化

**现状**：有"本类型隐式参考"提示、"沿用此方向"按钮、
"已确认方向"徽章、"取消确认"按钮。整个系统很强大，但用户不一定理解
"隐式参考"是什么意思、"沿用此方向"会发生什么。

**精简方案**：
- "沿用此方向" → "设为默认风格"（更直白）
- "隐式参考" → "默认风格"（用户语言）
- "已确认方向"徽章 → 一个小的 ✓ 图标 + tooltip 说明
- 不减少功能，只是换一套用户能理解的说法

**工作量估计**：XS — 纯文案替换

---

#### 2.9 右侧详情面板默认折叠

**现状**：三栏布局，右侧面板一直在那里，展示编译结果、验证结果等。
对新用户来说信息密度太高了。

**精简方案**：
- 右侧面板默认折叠成一个侧边标签（"< 详情"）
- 点击后展开
- 生成成功后自动展开一次（展示验证结果等关键信息），用户关闭后保持关闭
- 或者：干脆把详情合并到中间预览区的下方，用 Tab 切换

**理由**：
- 新用户的注意力应该在左侧配置 + 中间预览
- 右侧面板是"检查/调试"用的，不是核心创作流程
- 少一栏 = 少一份认知负担

**工作量估计**：M — 需要重新考虑布局和信息架构

## 4. 实施建议

### 顺序：从小到大，快速验证

| 阶段 | 做什么 | 工作量 | 预计收益 |
|------|--------|--------|---------|
| **第 1 步** | 合并编译+生成 + Logo 自动判断 + 反馈按钮折叠 | XS + XS + XS | 立竿见影，1 天能做完 |
| **第 2 步** | 参考优先模式自动化 + must_include/must_avoid 合并 | S + S | 减少 2 个主要决策点 |
| **第 3 步** | 模板化选择（类型+子类型+镜头合并） | M | 最大的体验提升 |
| **第 4 步** | 右侧面板折叠 + 术语替换 | M | 信息密度降低，整体更清爽 |

### 关键约束

- **后端零改动**：所有精简都在前端 UI 层
- **功能不删除**：只是藏起来或合并，高级用户依然能找到
- **协议不变更**：`application-contracts.ts` 一个字都不改
- **渐进式**：每一步都可以独立发布、独立验证

### 验证方式

虽然没有外部用户，但我们可以用**内部可用性测试**：
- 找 3 个不熟悉产品的同事（比如后端工程师）
- 给他们一个任务："生成一张咖啡店的前台效果图"
- 记录完成时间、出错次数、问了多少问题
- 精简后再测一次，对比数据

内部测试虽然不如真实用户，但足以验证"复杂度是否真的降下来了"。
