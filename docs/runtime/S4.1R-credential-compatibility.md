# S4.1R Credential Compatibility

## Storage decision

Electron Desktop continues to use Electron `safeStorage`. The Node Web host uses the existing Shared Runtime `readCredentials(profileId)` boundary with a Node adapter:

1. `MASTERPIECE_API_KEY_<PROFILE_ID>` environment override;
2. `MASTERPIECE_API_KEY` process-level environment override;
3. AES-256-GCM encrypted local credential file under `node-credentials/`.

The local AES key and encrypted payloads are runtime files with restrictive file modes. They are not repository assets and must never be committed. API keys are never returned by `settings:get` and never enter Browser Renderer state.

## Electron compatibility

The Node adapter reads the same `settings.json` profile metadata and `defaultDataPath`. It deliberately does not decrypt, copy or rewrite Electron `safeStorage` blobs. Existing Desktop profiles remain visible, but the user must provide the key once through the Node-backed settings UI or environment. This is an explicit compatibility boundary, not a silent credential migration.

## Data compatibility

Project data is not tied to the secret store. The configured `defaultDataPath` remains authoritative, so existing projects, reports and generated assets remain at their current locations.
