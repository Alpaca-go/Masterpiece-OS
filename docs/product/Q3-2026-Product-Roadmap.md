# Product Roadmap — Masterpiece OS 5.x — Q3 2026

> **方向校准**：本路线图从"技术交付驱动"转向"用户结果驱动"。
> 每一项都对应一个具体的用户问题和可衡量的成功指标，而不是一个功能列表。
> 技术门禁是底线，不是终点。

---

## 🌟 北极星指标

**每周成功完成首次生成的新用户数**

> 为什么是这个：它同时衡量了获客（多少人来试）、激活（多少人学会用）、
> 和核心价值交付（生成成功 = 工具工作了）。如果这个数字在涨，
> 说明产品在正确的方向上；如果不涨，其他一切指标都没有意义。

**当前基线**：未知（尚未埋点）
**Q3 目标**：建立度量基线，并在季末达到周环比正增长

## 🟢 Now — 当前季度（8–9 月）

已承诺的工作。PM、设计、工程完全对齐。

### Initiative 1: 产品度量体系落地

**用户问题**：我们不知道用户在产品里经历了什么——哪里卡住、哪里放弃、
哪里真正获得了价值。所有决策都基于内部直觉，而不是用户证据。

**成功指标**：
- 核心漏斗（创建→上传→生成→成功→再次生成）有实时数据看板
- 生成失败原因分类覆盖率 100%
- 团队每周 review 产品指标数据

**交付物**：
- [ ] 后端：operation 层统一埋点（start / complete / fail / duration）
- [ ] 前端：关键页面 + 关键操作埋点
- [ ] 失败原因分类体系（Provider 错误 / 超时 / 输入问题 / 系统 Bug）
- [ ] 本地日志 + 简单 JSON 导出（暂不上复杂分析平台）
- [ ] 每周指标快照脚本（一键生成本周数据摘要）

**Owner**：待定  **ETA**：Week 1–2
**风险**：Low — 技术简单，关键是坚持看数据

---

### Initiative 2: Short-Chain 首次使用体验重构

**用户问题**：新用户打开产品后，不知道下一步该做什么、不知道
"Short-Chain"是什么意思、生成过程中看不到进度、失败了不知道怎么办。
当前 UI 是内部工程师的语言，不是用户的语言。

**成功指标**：
- 新用户首次生成成功率从基线提升 ≥ 20 个百分点
- 用户无需阅读文档即可完成首次生成
- 生成中用户不刷新页面（通过进度透明度衡量）

**交付物**：
- [ ] 空状态重新设计：一句话说清"这是什么、你该做什么"
- [ ] 引导式首次体验：分步引导（上传文档 → 确认品牌信息 → 选场景 → 生成）
- [ ] 生成进度透明化：分阶段展示（分析中 → 编译中 → 生成中 → 即将完成）
- [ ] 错误状态重新设计：告诉用户"发生了什么、你可以做什么、我们在做什么"
- [ ] 术语替换：把内部术语（Short-Chain、Reference Anchor、Brief 等）
      换成用户能理解的语言

**Owner**：待定  **ETA**：Week 2–6
**风险**：Medium — 需要先做用户可用性测试验证方向

---

### Initiative 3: 生成失败的降级与恢复

**用户问题**：当 Provider 出问题、网络超时、或内容违规时，用户看到的
要么是空白、要么是技术报错。用户感觉"工具坏了"，而不是"这次没成功，
可以换个方式试试"。

**成功指标**：
- 生成失败率 < 5%
- 失败场景中，用户主动重试率 ≥ 40%
- 因失败导致的 7 天流失率 < 基线 + 10pp

**交付物**：
- [ ] 失败原因分类 + 用户友好的错误文案（不说"500 Internal Server Error"）
- [ ] 智能重试：临时性错误自动重试 1 次（透明告知用户）
- [ ] 降级策略：Provider 不可用时，提示用户切换模型或稍后再试
- [ ] 部分成功：多张图中部分成功时，展示成功的 + 标记失败的 + 单张重试
- [ ] 失败反馈入口：一键"告诉我们哪里不对"（带运行 ID，方便排查）

**Owner**：待定  **ETA**：Week 4–7
**风险**：Medium — 需要 Provider 层错误分类标准化

## 🟡 Next — 未来 1–2 个季度（Q4 2026）

方向性已承诺，开发前需要进一步定义范围和用户验证。

### Initiative 4: 品牌一致性体验强化

**假设**：如果用户能明显感受到"生成的图片忠实于我的品牌规范"，
他们会更频繁地使用，并且愿意为这个能力付费。

**预期结果**：
- 同品牌项目的重复生成率 ≥ 50%
- "品牌一致性"成为 NPS 推荐者的 Top 3 提及理由

**验证前置条件**：
- 先做 5 次用户访谈，确认"品牌一致性"是核心痛点
- 在现有用户中做小样本可用性测试

---

### Initiative 5: 批量生成能力

**假设**：当用户需要一次生成一组（4–8 张）相关图片时，
单张生成的效率太低，批量生成是高阶用户的刚需。

**预期结果**：
- 活跃用户中 ≥ 20% 使用批量生成
- 批量生成用户的周使用频次是单张用户的 1.5x

**验证前置条件**：
- 分析现有行为数据，确认有多少用户在短时间内连续生成多张
- 访谈 3–5 个高频用户，了解他们的批量场景

---

### Initiative 6: 产物库与版本管理

**假设**：用户需要管理和复用之前的生成结果，而不是每次从零开始。
好的产物库能提升留存和使用频次。

**预期结果**：
- 7 天内回访产物库的用户比例 ≥ 40%
- 从历史产物重新编辑/衍生生成的比例 ≥ 20%

**验证前置条件**：
- 观察现有用户是否有"反复生成同主题"的行为模式

## ❌ 我们不做的事（以及为什么）

> 公开说"不"可以防止重复请求并建立信任。
> 每一个"是"都是对其他事情的"不"。

| 请求 / 方向 | 来源 | 延后原因 | 重新考虑条件 |
|------------|------|----------|-------------|
| Creative Intelligence 继续深度迭代 | 内部技术驱动 | 未验证用户价值；投入产出比不明确 | 10+ 用户明确表示需要，或有数据证明 CI 提升核心指标 |
| 移动端适配 | 内部讨论 | 桌面端核心体验还没打磨好；移动端使用场景不明确 | 有数据显示 ≥ 15% 访问来自移动端，或有明确移动场景需求 |
| 自建模型 / 模型微调 | 技术好奇 | 成本高、周期长；当前阶段 Provider 抽象层已足够 | 单位经济模型显示自研能显著降低成本，或有独占性质量优势 |
| 插件 / 开放 API | 平台化想象 | 产品核心价值还未验证；过早平台化是常见陷阱 | 核心留存指标稳定（D30 ≥ 30%），且有开发者主动请求接入 |
| 营销网站 / 品牌包装 | 市场驱动 | 产品本身还没准备好；营销带来的用户只会失望地流失 | 首次生成成功率 ≥ 60% 且 7 天留存 ≥ 30% |

## 📝 决策记录

### 2026-08-24：路线图方向校准

**背景**：项目 5.0-rc.1 技术架构已稳定（S5 Desktop 移除完成），
但产品方向、用户画像、成功指标均未明确。

**决策**：
1. Q3 核心目标从"交付功能"转向"验证产品价值"
2. 最高优先级是建立度量体系和用户反馈闭环
3. Short-Chain 体验重做必须以用户测试结果为输入，不做内部拍脑袋的设计
4. Creative Intelligence 暂不投入新功能开发，维持现有状态

**依据**：
- 产品成功 = 用户获得价值，不是代码通过测试
- 没有度量就没有改进，度量体系是一切产品决策的基础
- 在核心体验没打磨好之前，加更多功能只会增加混乱

**决策**：同意冻结 Creative Intelligence 新功能开发一个季度（Q3），
维持现有能力，不投入新迭代。资源转向 Short-Chain 体验和度量体系。

**决策**：同意将"Short-Chain"等内部术语替换为用户语言。
**约束**：只改 UI 层的展示文案和命名，不改变后端协议、不改变功能架构和运行逻辑。
前端通过 i18n/文案层做映射，后端 API 接口、类型名、内部变量名保持不变。

**决策**：北极星指标定为「每周成功完成首次生成的新用户数」。
Q3 的核心是建立基线并驱动增长，暂不以留存或收入为北极星。
