# 隔窗可见与未映射场景：独立接口审核提案

状态：未实现、未批准。本次没有新增生产 schema、持久化字段、Prompt 模板或 Provider 参数。

现有 `subtype`、`shot`、`shotSource` 能指定目标场景与相机表达；`userConfirmedFields` 能确认整组分析字段，但没有把具体室内节点与某个橱窗、观察位置、遮挡条件及授权来源绑定。`functionalRelationships` 中的一句“透过玻璃可见厨房”也没有这些信息。材质透明度或模型提案不能代替窥见室内的权限。因此不能把窗户关键词作为宽松默认。

| 待审核案例 | 当前处理 | 尚缺的决定 |
| --- | --- | --- |
| 临街玻璃局部可见制作、热气或顾客，且用户明确允许 | `review_required`，保存原句，不渲染该室内活动 | 具体窗口、观察位置、允许可见的节点/行为、范围与来源 |
| 外立面明示不允许看到厨房或堂食内部 | 保留负向边界约束；室内实体不取得渲染权威 | 无需放宽 |
| 店员在外立面室外递交、打包商品 | 有当前场景位置证据时可见 | 经营事实仍按输入证据等级，不升级为实测 |
| 入口店员递交商品 | 按入口原句保留；不会同时展开全店网络 | 无需新增窗口权限 |
| `exhibition`、`interior_panorama`、`counter` | UI 有模板选项，但无对应权威功能程序，明确阻断 | 单独审核场景映射，不把它们偷偷映射到入口/堂食 |
| `custom` / 其他未解析场景 | 无现成显式目标功能程序时阻断 | 自定义场景的权威与局部投影协议 |

建议另立接口评审，讨论显式的一次请求级可见性授权：目标镜头、观察点/窗口绑定、允许看到的目标节点或行为、局部范围/遮挡限制、证据引用及用户确认状态。上述只是所需信息类别，不是已批准的字段名或 schema。

审核需明确：仅授权列出的局部内容；未列出内容继续依赖或待审；负向视线约束优先；材料透明不能自动产生权限；模型建议不能自行确认；缺少可验证绑定时拒绝或待审；不能用完整功能网络推导窗口内全店可见。需设计中英文正反例，并证明公开操作仍受 B1、完整性和零参考图门禁控制。

当前玻璃“正例”只证明应能表达的需求被准确保留为待审，**不是可见性已获准的生产通过案例**。详见 `supplementary-evidence.json` 的 `glass-request` 与 `glass-negative`。此次到此停止接口实现，避免越过文档禁止新增字段的边界。
