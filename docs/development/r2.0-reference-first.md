## 0. 背景与问题陈述

R10.4 阶段我们把 vNext 跨场景生图链路打通到「Provider 真发 → 真回图」
的程度（R10.4 final smoke 见
`space-generator/quality-baselines/r10-final/R10-FINAL-ACCEPTANCE.md`），
但链路里仍存在 **3 类**跨场景 Reference-First 相关问题：

1. **后分析上传静默丢失** — `vnext-service.start` 用 `flatMap` 过滤
   显式 reference ID；分析后才上传、但 `sourceAssetRefs` 还没刷新的资产
   ID 会得到 `[]`，再触发 `SPACE_REFERENCE_FIRST_REFERENCE_REQUIRED`
   失败，且无任何线索告诉用户哪些 ID 丢了。
2. **Reference-First 容易退化成 1:1 复制** — 用户拿一张参考图期望"继承
   设计语言，但生成**另一个**功能场景"，Seedream 5.0 Pro 经常把参考
   图的**场景/构图/功能程序**整体照搬，结果图几乎就是参考图的另一个
   视角，而不是目标场景。
3. **UI 5 状态折叠** — 验证 / 纠偏流程被压成单一 `passed / failed`
   徽标；首次图（用户唯一能接受的）若因纠偏失败被替换，必须翻历史
   才能找回。

R2.0 是按以下顺序修复的：**先把"丢不丢"搞清楚（§4.11）** →
**再把"像不像"约束表达清楚（§4.10）** → **再把"修不修"流程
做到不丢首图（§4.13）** → **最后做"复不复制"的多模态审计（§6.7）**
与**证据闭环（§8）**。

## 4. §4.9 — `referenceSceneRelation` 辅助元数据（Phase B-1）

### 4.9.1 设计意图

`VNextReferenceSceneRelation = "same_scene" | "cross_scene" | "unknown"`
是**辅助元数据**，告诉编译器 / Provider / UI 如下单一信息：
"参考图的场景，与本次任务的目标场景，是同一类场景，还是不同类场景，
还是用户没声明"。它**不**替代 Target Scene Functional Authority
（R11.2.3 引入的"目标场景拥有功能层权威"），也**不**是新产品模式。

### 4.9.2 行为契约

- `reference_first` 任务：可以携带 `referenceSceneRelation`，白名单
  校验；任何其它值（`undefined` / `null` / 错值 / 非字符串）一律
  退化为 `"unknown"`，**永不抛错**。
- `standard` 任务：**省略**该字段。
- `continuation` 任务：**省略**该字段（`world_consistency` 已经
  表达了 relation，再加就是冗余 + 误导）。
- 该字段**永不允许**进入 route integrity 任何 throw-on-fail 路径。
  B-3 / B-2 读它；缺失或非法时必须按"unknown"行为继续。

### 4.9.3 接入点

| 层 | 改动 |
|---|---|
| 合约 | `VNextReferenceSceneRelation` 联合类型；`VNextTaskContract.referenceSceneRelation?` 可选 |
| 桌面类型 | `apps/desktop/src/shared/types.ts` 同步导出 |
| 编译 | `packages/image-generation-runtime/src/vnext/task-contract.js` 白名单 + 退化 |
| UI | `VNextGenerationWorkspace.tsx` 新增 `<select>`（仅在 `reference` basis 可见）；`title` 属性明示"辅助 + 不替代" |

### 4.9.4 测试

`tests/image-generation/space-r2-b1-reference-scene-relation.test.js` —
8 cases，钉住：默认 unknown、保留 same_scene、保留 cross_scene、
非法值退化、null 退化、standard 省略、continuation 省略、bogus 输入
永不抛错。

## 5. §4.10 — 适配器能力声明 + Product Policy + Reference Boundary

### 5.1 §4.10 Path A — 适配器能力声明（Phase B-2）

#### 5.1.1 设计意图

`maxReferences` 不能是 vnext-service 里硬编码的 `2`。它必须由
**Product Policy**（业务允许每种 basis 用多少张）和 **Adapter
Capability**（模型实际能接收多少张）共同决定，取**最小值**。如果
adapter 没有声明 capability，按 0 处理（**fail-closed**），绝不让
未验证的 adapter 收到"凭感觉"的 reference。

`referenceStrengthControl` / `referenceRoleControl` 必须**诚实**：
**未经端到端验证前，强制 `supported: false`** + `note` 说明。这条
原则优先于"功能丰富"——避免 Provider 收到一个不知道有没有用的参数。

#### 5.1.2 类型与模块

```ts
// packages/image-generation-contracts/src/index.ts
interface VNextAdapterStrengthControlCapability {
  supported: boolean;
  controlParameter: string | null;
  note: string;
}
interface VNextAdapterReferenceCapability {
  maxReferenceImages: number;
  referenceStrengthControl: VNextAdapterStrengthControlCapability;
  referenceRoleControl: VNextAdapterStrengthControlCapability;
}
interface VNextAdapterCapability {
  adapterId: string;
  adapterVersion: string;
  reference: VNextAdapterReferenceCapability;
}

// packages/image-generation-runtime/src/space/product-policy.js
const PRODUCT_POLICY_DEFAULT_MAX_REFERENCES = {
  standard: 0,
  reference_first: 2,
  continuation: 1,
};
function resolveEffectiveMaxReferences({
  generationBasis, adapterCapability,
}): { effectiveMax: number; source: 'product_policy' | 'adapter_capability' };
```

#### 5.1.3 接入点

| 层 | 改动 |
|---|---|
| 合约 | `VNextAdapterReferenceCapability` 等三个新类型 |
| Seedream adapter | `createSeedreamVNextAdapter()` 暴露 `capability` 字段（frozen），`maxReferenceImages = 2`，`referenceStrengthControl.supported = false` |
| vnext-service | `start` 用 `resolveEffectiveMaxReferences` 取代硬编码 `2`；非 space 路径的 `.slice(0, 2)` 不动（属于另一范畴） |
| space/index.js | re-export `PRODUCT_POLICY_VERSION` / `resolveProductPolicyMaxReferences` / `resolveEffectiveMaxReferences` |

#### 5.1.4 测试

`tests/image-generation/space-r2-b2-adapter-capability.test.js` —
13 cases，钉住：

- Policy per-basis 上限
- Seedream capability 形状
- `referenceStrengthControl` / `referenceRoleControl` 都报 UNSUPPORTED
- effective max：`standard = 0`、`reference_first = min(2, 2) = 2`、
  `continuation = 1`
- 缺 adapter capability → effective max = 0（fail-closed）
- policy 紧于 capability → policy 胜，`source = 'product_policy'`
- capability 紧于 policy → capability 胜，`source = 'adapter_capability'`
- adapter / capability / control 对象全部 frozen

#### 5.1.5 Commit

- `3690cf3` feat(space): Seedream adapter declares capability; Product
  Policy + Capability jointly decide maxReferences (r2.0 B-2)
  测试：root 576 → 589 (+13)，desktop 272 → 272

### 5.2 §4.10 Path A fallback — Reference Boundary 文本块（Phase B-3）

#### 5.2.1 设计意图

B-2 把 Path A（Provider 端的 `ref_strength` / role 显式参数）报为
unsupported。**诚实的回退**是：写一段**正向表达**的 Reference
Boundary 文本块（v2.0 风格），告诉模型"保留什么"+"不保留什么"。
**不**用否定式（"不要复制参考"），而用正向列出"保留设计语言"
+"让目标场景功能驱动程序"。

#### 5.2.2 模块

```js
// packages/image-generation-runtime/src/space/reference-boundary.js
const REFERENCE_BOUNDARY_VERSION = 'space-reference-boundary@1.0.0';
function renderReferenceBoundary({
  generationBasis, referenceSceneRelation, targetSceneLabel, adapterCapability,
}): string | null;
```

行为表：

| basis | referenceSceneRelation | 行为 |
|---|---|---|
| `standard` | （任意） | 返回 `null`（text-only） |
| `continuation` | （任意） | 返回 `null`（`world_consistency` 已经更具体） |
| `reference_first` | `cross_scene` | 追加：different functional class; inherit design language only |
| `reference_first` | `same_scene` | 追加：same functional class; keep design language and allow legitimate variation within the scene |
| `reference_first` | `unknown` | 追加：relation not declared; inherit design language only and let the target scene function drive the program |

边界块**显式**地根据 `adapterCapability.reference.referenceStrengthControl.supported`
加一句话：

- supported: "Use the official `ref_strength` parameter."
- **unsupported（当前 Seedream 5.0 Pro 现状）**: "Provider weight / role
  controls are not available for this model. The text above is the only
  boundary; do not invent or assume additional controls."（**fail-honest**）

#### 5.2.3 接入点

- `seedream-adapter.js#compile` 在 `reference_first` 时调用
  `renderReferenceBoundary`，**追加**（非前置）到 compiled prompt，
  分隔符 `"\n\n"`；标签 `"REFERENCE BOUNDARY (high-priority instruction)"`
  让模型把它当顶层指令。
- **追加后重测 12_000 字符上限**；超预算即抛错（不会让超 cap prompt
  真的到 Provider）。
- compile 结果新增 `referenceBoundary: { applied, version, providerStrengthControl, promptCharacters }`。

#### 5.2.4 测试

`tests/image-generation/space-r2-b3-reference-boundary.test.js` —
14 cases，钉住：版本号、standard 永不追加、continuation 永不追加、
reference_first × cross_scene / same_scene / unknown 三种 intent line、
unsupported / supported 两种 strength 提示、Seedream compile 集成、
字符上限重测、ref 列表为空时不崩。

#### 5.2.5 Commit

- `35f95f5` feat(seedream): Reference Boundary text block (v2.0-style
  positive expression) (r2.0 B-3)
  测试：root 589 → 603 (+14)，desktop 272 → 272（无新 desktop 测试）
- 桌面 B-3 之前已通过 `image-generation:preflight-reference-assets`
  增量验证（B-3 改了 compile 链路但不动 desktop）。

## 6. §4.11 — Reference Asset Resolver + UI preflight

### 6.1 §4.11 — Phase A0：最小修复（`aacc09f`）

FORMAT_UNSUPPORTED 显式错误）。

### 6.2 §4.11 — Phase C-1：Reference Asset Resolver 模块（`2c81402`）

**问题**：A0 只解决"静默丢"，没解决"为什么不能用作 reference"。

**模块**：`apps/desktop/src/main/reference-asset-resolver.ts`

```ts
type ReferenceResolutionFailure = {
  assetId: string;
  code:
    | 'REFERENCE_ASSET_NOT_FOUND'         // ID 不在 project.assets
    | 'REFERENCE_ASSET_NOT_READY'         // status !== "ready"
    | 'REFERENCE_ASSET_FORMAT_UNSUPPORTED' // 签名非 PNG/JPEG/WebP
    | 'REFERENCE_ASSET_PATH_INVALID'      // 路径越出 project root
    | 'REFERENCE_ASSET_FILE_UNREADABLE'   // fs.open / fs.read 失败
    | 'REFERENCE_ASSET_FILE_TOO_LARGE'    // 超过 maxReferenceBytes（默认 12MB）
    | 'REFERENCE_ASSET_SHA_MISMATCH';     // verifySha256=true 时哈希不匹配
  message: string;
};
async function resolveReferenceAssets(
  explicitIds: string[],
  options: { projectRoot: string; verifySha256?: boolean; maxReferenceBytes?: number },
  projectAssets: ReadonlyArray<{ assetId: string; ... }>,
): Promise<{ resolved: ResolvedReferenceAsset[]; failures: ReferenceResolutionFailure[] }>;
```

**设计要点**：
- **纯函数**（不依赖 Electron / IPC 单例）
- 输入只接 `ProjectAsset[]` + `projectRoot`；不读 Settings、不读 credentials
- SHA 校验默认 **off**（project store import 时记录 SHA；post-import
  篡改是另一范畴，由 `REFERENCE_ASSET_SHA_MISMATCH` 暴露，开关
  `verifySha256: true` 时启用）
- MIME 校验**按签名**，不是按扩展名（防 .pdf 重命名 .png）

**测试**：`apps/desktop/tests/reference-asset-resolver.test.ts` — 18 cases。

### 6.4 §4.11 — Phase C-3：UI preflight（`b37c6fc`）

**目标**：让用户在 **点 "use as reference" 之前** 就能看到每个资产的
解析状态（✓ resolved / ✕ code / · pending）。失败资产**禁用复选框**
（hover 提示失败原因），因为 vnext-service.start() 会在 submit 时
抛同样的 code。

**链路**：

```
renderer (VNextGenerationWorkspace)
  → preload (imageGeneration.preflightReferenceAssets)
  → IPC channel (image-generation:preflight-reference-assets)
  → vnext-service.preflightReferenceAssets
  → Reference Asset Resolver
```

**关键设计**：

- **fail-soft**：从不抛；按 ID 返回 `{ resolved | failed }`。
- **去重**：duplicate IDs 在 Resolver 前去重。
- **条件注册**：`image-generation:preflight-reference-assets` 只在
  `vnextService.preflightReferenceAssets` 存在时注册（旧的 vnext
  service 不会让 IPC 启动崩）。
- **同一 Resolver**：UI preflight 和 vnext-service.start() 用**同一
  份代码**，preflight pass ⇒ submit 不会抛 `REFERENCE_ASSET_*`。

**接入点**：

| 层 | 改动 |
|---|---|
| 共享类型 | `PreflightReferenceAssetsInput` / `ResultEntry` / `ResolvedRecord` / `FailureRecord`（JSON 序列化，结构化克隆可走） |
| 服务 | `vnext-service.preflightReferenceAssets({ projectId, assetIds })` |
| IPC | `image-generation:preflight-reference-assets` |
| Preload | `imageGeneration.preflightReferenceAssets` |
| UI | `referencePreflight: Record<assetId, ResultEntry>` 状态；`runPreflight(assetIds)` 在 `loadProjectAssets` 后 / `uploadReferenceImage` 调 |
| CSS | `.asset-tile.disabled-preflight` / `.preflight-badge` (ok / fail / pending) |

## 7. §4.13 — 双门禁拆分 + 5 状态 UI + first-image 保留

### 7.1 §4.13 — Phase D：双门禁拆分（`70ae270`）

#### 7.1.1 设计意图

`assertSpaceGenerationRouteIntegrity` 一个函数同时管两件事：

1. **编译期完整性**（block 顺序 / 字符预算 / compiler id / spatial
   semantic report / aspect ratio）—— 只读 FROZEN 编译产物
2. **Provider prompt sanity**（字符数 / 角色标记）—— 必须跑在 Provider
   实际收到的 prompt 上（可能 ≠ 编译产物，因 user edit / validator
   correction）

合并时，**user-edited / correction prompt** 可能错误触发
`SPACE_COMPILER_ROUTE_MISMATCH`，阻挡**合法的**纠偏重试。

#### 7.1.2 拆分

| 门 | 模块 | 失败码 | 跑在 |
|---|---|---|---|
| **Gate A** (compile-time) | `gates/compile-integrity-gate.js` `assertSpaceGenerationRouteGateA` | `SPACE_COMPILER_ROUTE_MISMATCH`（及 compile-route 衍生） | 编译产物（**永不读** `input.editedPrompt`） |

### 7.2 §4.13 — Phase E：5 状态 UI + first-image 保留（`6fbd17c`）

#### 7.2.1 设计意图

当前 UI 把验证 / 纠偏折叠成单 `passed | failed | unverified` 徽标。
当**首次图**是用户唯一想要的东西时，纠偏失败（`correction_start_failed`
或 `correction_still_failed`）会**把首图从 UI 上替换掉**，用户必须
翻历史才能找回。**r2.0 §4.13 引入更细的 5 状态 + first-image 保留**。

#### 7.2.2 5+1 状态

```ts
type VNextGenerationFlowState =
  | 'initial_failed'              // 1: 首次 Provider 直接失败
  | 'awaiting_validation'         // 2: 首次 OK，等验证 / 收验证
  | 'correcting'                  // 3: 首次验证失败，纠偏 prompt 已发
  | 'correction_start_failed'     // 4: 纠偏 Provider 直接失败
  | 'correction_still_failed'     // 5: 纠偏 Provider 成功但验证仍失败
  | 'passed';                     // terminal: 验证通过（首次或纠偏）
```

旧的 `terminalStatus: 'passed' | 'failed' | 'unverified'` **保留**，
`flowState` 是更细的编码（`flowState ∈ {passed}` 包含 `terminalStatus = passed`；
其它 4 种 flowState 折叠成 `terminalStatus = failed`；`flowState =
awaiting_validation` 折叠成 `terminalStatus = unverified`）。

#### 7.2.3 辅助函数

```ts
function deriveGenerationFlowState(input: VNextGenerationFlowInput): VNextGenerationFlowState;
```

签名**只接 components**（`initialRun` / `initialValidation` /
`correctionRun` / `correctionValidation`），不接 `VNextValidatedGenerationResult`，
避免循环类型依赖。

推导顺序（按优先级）：

1. `initialRun.status !== 'succeeded'` → `'initial_failed'`
2. `!initialValidation` → `'awaiting_validation'`
3. `initialValidation.status !== 'failed'` → `'passed'`
4. `initialValidation.retryRecommended !== true` → `'passed'`
5. `!correctionRun` → `'correcting'`
6. `correctionRun.status !== 'succeeded'` → `'correction_start_failed'`
7. `!correctionValidation` → `'correcting'`
8. `correctionValidation.status === 'failed'` → `'correction_still_failed'`
9. else → `'passed'`

## 10. §9 — 纠偏是运行时叠加 / 回滚策略（Phase D 落地）

### 10.1 设计意图

纠偏是**运行时叠加**，不是"重新编译"。v2.0 计划明文：

> 纠偏是运行时叠加。

含义：

1. compile artifact directory（`compilations/<taskId>/trace.json`）是
   **不可变事实**——它记录"那次编译是什么样"。**绝不**因
   start / correction retry 而被改写。
2. 每次 start / correction 写一个**独立**的 `run-trace.json`，作为
   run-level metadata。
3. 错误码双门禁：
   - `SPACE_COMPILER_ROUTE_MISMATCH`（Gate A）—— 编译产物本身坏了
   - `SPACE_PROVIDER_PROMPT_INVALID`（Gate B）—— Provider 实际收到
     的 prompt 有问题（user edit / correction / 超 cap）
4. **Rollback**：Gate B 可独立 no-op 化（v2.0 明文要求"门禁 B 可
   独立回滚为单一门禁"），恢复合并行为。

### 10.2 Phase D 已落

见 §7.1.3、§7.1.4、§7.1.6。
